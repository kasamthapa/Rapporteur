## 2. JSON schema for `result`

Top-level envelope, matching CLAUDE.md's spec exactly, plus the fields needed later without adding verification logic now.

```ts
type ActionStatus = "committed" | "suggested";

interface EvidenceRef {
  evidenceQuote: string;   // exact-ish quote from transcript the model is citing
  agendaItem: string;      // must match one of agendaCoverage[].item, or "Off-agenda"
  // verified: reserved field name, intentionally OMITTED from item 1's output.
  // Item 2 adds `verified: boolean | null` after server-side quote matching.
  // Leaving it out now keeps item 1's contract honest: nothing item 1 computes
  // should claim to be verified. Documented here so item 2 knows the exact
  // insertion point and field name to add without reshaping the schema.
}

interface Decision extends EvidenceRef {
  text: string;              // the decision itself, plain language
}

interface ActionItem extends EvidenceRef {
  text: string;               // what needs to be done
  owner: string;               // "unassigned" if not stated — never invented
  deadline: string;             // "none" if not stated — never invented
  status: ActionStatus;          // "suggested" for "maybe/should we", "committed" for firm commitments
}

interface AgendaSection {
  agendaItem: string;         // exact text of the agenda topic (given or inferred)
  summary: string;             // prose summary of discussion for this item; "" not omitted if item was never discussed (see agendaCoverage instead — see note below)
}

interface AgendaCoverageEntry {
  item: string;               // agenda topic text
  discussed: boolean;          // false =&gt; never discussed in transcript
}

interface OffAgendaEntry extends EvidenceRef {
  text: string;                // what was discussed off-topic
  // agendaItem is fixed to the literal string "Off-agenda" for entries in this array
}

interface MeetingResult {
  meetingTitle: string;                  // echoed back from request
  agendaGiven: boolean;                   // true if user supplied agenda topics
  agendaInferred: boolean;                 // true if agenda was model-generated (agendaGiven === false)
  agenda: string[];                         // the agenda actually used — user's list, or model-inferred list
  summaryByAgendaItem: AgendaSection[];      // one entry per agenda item in `agenda`, in order
  decisions: Decision[];                      // [] if none — never omitted, UI must say "No decisions recorded"
  actionItems: ActionItem[];                   // [] if none — same rule
  offAgenda: OffAgendaEntry[];                   // [] if nothing off-topic
  agendaCoverage: AgendaCoverageEntry[];          // one entry per agenda item; discussed:false for topics never discussed
  meta: {
    transcriptLineCount: number;                  // number of parsed transcript lines fed to the model
    generatedAt: string;                            // ISO timestamp, server-set, not model-set
  };
}
```

Notes on edge cases baked into the schema:
- "No agenda given → group by inferred topics, say so in UI": `agendaGiven: false`, `agendaInferred: true`, and `agenda` is populated with the model's inferred topics. The client reads this flag to render a banner ("Agenda was inferred from the transcript").
- "Meeting with no decisions/action items (say so, not omit)": arrays are always present (possibly empty `[]`); it is the *client's* job (item 3, but ResultPreview should do the minimal version now) to render "No decisions recorded" when `decisions.length === 0` rather than the server inventing placeholder text. Server never emits sentinel strings like "No decisions found" inside the array itself — that would be inventing content. This is a explicit design decision worth flagging to the user before implementation.
- "Item with no owner → 'unassigned'", "no deadline → 'none'": literal enforced string values, checked by the zod schema (`z.enum` is too strict since deadline could be a real date/phrase — use `z.string().min(1)` and rely on prompt instructions + the "never invent" rule instead; validation only enforces non-empty string, not enum, since deadlines are freeform text like "next Friday" or "none").
- `status: committed | suggested` is a strict enum in the zod schema — if Gemini returns anything else, that's an invalid-schema case → triggers the retry-once-then-error flow.
- `verified` is explicitly reserved and NOT part of item 1's schema — see inline comment above. This directly answers the prompt's request to decide on this: **lean toward omitting it entirely in item 1**, since emitting an always-null/always-false field that item 2 will later compute is a wasted round-trip and risks the client treating "not yet verified" as "verified: false" (a false negative shown as fact-checked, which contradicts CLAUDE.md's trust principle). Item 2 will add the field additively — this is a backward-compatible schema change, not a breaking one, so there's no cost to deferring it.

## 3. API endpoint(s)

**Single synchronous endpoint**: `POST /meetings`

Justification for one endpoint over a create+poll pattern: Gemini 2.5 Flash on a single ~1-hour, 8-speaker transcript is expected to respond in low single-digit seconds to maybe 15-20s worst case — well within a typical HTTP timeout (Express default has none; client fetch has none unless set). A two-step create-then-poll design adds a job queue, a status column, and client polling logic — all "abstraction for later" that CLAUDE.md's "keep it simple" rule argues against for a hackathon scope. If real-world latency testing later shows Gemini is too slow, that's a follow-up decision, not a day-1 one. Documented as a decision to flag, not silently assumed.

### Request

`POST /meetings`
Content-Type: `application/json`

```ts
{
  title: string;                 // required, non-empty
  agenda: string[];               // optional, defaults to [] if omitted — [] means "no agenda given"
  transcript: string;              // required, raw pasted/uploaded text
}
```

Note: file upload. CLAUDE.md's item 1 says "paste/upload transcript." Since transcript is plain text (not audio — audio is item 8, explicitly out of scope), an uploaded `.txt` file can be read client-side via the browser's File API (`file.text()`) and sent as the same `transcript` string field — **no multipart/multer needed on the server**. This avoids adding a new server dependency for something the browser already solves. Flagging this as the chosen approach rather than assuming multer, since CLAUDE.md requires justifying every dependency choice.

### Success response — `201 Created`

```ts
{
  id: string;              // meetings.id from Supabase insert
  result: MeetingResult;    // as defined above
}
```

### Error responses

| Case | Status | Body |
|---|---|---|
| Missing/empty `title` | 400 | `{ error: "title is required" }` |
| Missing `transcript` | 400 | `{ error: "transcript is required" }` |
| Transcript too short (e.g. &lt; some minimum meaningful length / no parseable lines) | 400 | `{ error: "transcript is too short to summarize" }` |
| Transcript parses to zero valid lines (all malformed) | 400 | `{ error: "no valid speaker/timestamp lines found in transcript" }` |
| Gemini returns invalid JSON / fails schema validation twice (1 retry) | 502 | `{ error: "AI returned an invalid response after retry, please try again" }` |
| Gemini 429 rate limit | 429 | `{ error: "rate limited, retry in Xs" }` (X parsed from Gemini's retry-after if available, else a sane default e.g. 30) |
| Gemini other API error (network, 500, auth) | 502 | `{ error: "AI service error: &lt;clear message&gt;" }` |
| Supabase insert failure | 500 | `{ error: "failed to save meeting: &lt;clear message&gt;" }` |
| Unexpected server error | 500 | `{ error: "unexpected server error" }` |

All error bodies are plain JSON objects with a human-readable `error` string — no silently swallowed exceptions, per CLAUDE.md's rule. Every catch block either re-throws as one of the above shaped errors or is not written at all (let it propagate to a top-level Express error handler that formats the 500 case).

Flow inside the handler: validate request → parse transcript → build prompt → call Gemini → validate result against zod schema → (if invalid, retry once) → (if still invalid, 502) → insert into Supabase (`meetings` table, `result` column as jsonb) → return 201 with `id` + `result`.

## 4. Transcript parsing

### Expected input format

One line per utterance:
```
[HH:MM:SS] Speaker Name: utterance text
```
or a slightly looser accepted form `HH:MM:SS Speaker Name: utterance text` (brackets optional). This needs to be picked as *the* documented format and stated in the UI (placeholder text / helper text in the textarea) since there's no existing convention to reuse — greenfield project, so this is a product decision to confirm with the user before implementation, not something to infer from a competitor's export format we don't have access to.

### Parsing algorithm

Regex per line, applied after splitting the raw transcript on `\n`:

```
^\s*\[?(\d{1,2}:\d{2}(:\d{2})?)\]?\s*[-–—]?\s*([^:]{1,80}):\s*(.+)$
```
Captures: timestamp, speaker name, utterance text. Design choices:
- Timestamp accepts `MM:SS` or `HH:MM:SS` (long meetings need hours).
- Speaker name capped at 80 chars to avoid greedily eating the whole line if colons appear elsewhere in the name.
- Everything after the first `:` following the speaker is the utterance — utterance text is allowed to contain further colons.

### Line numbering

Every line in the raw transcript (before filtering) gets a 1-based `lineNumber` matching its position in the original text as pasted/uploaded, **not** the index among successfully-parsed lines. This matters because item 2's evidence verification will need to map an `evidenceQuote` back to an exact line in the *original stored transcript text* (the `transcript` column, stored verbatim). So:

```ts
interface ParsedLine {
  lineNumber: number;   // 1-based, position in original raw transcript
  timestamp: string | null;   // null if line didn't match the pattern
  speaker: string | null;
  text: string;           // the matched utterance, or the raw line if unmatched
  malformed: boolean;      // true if regex didn't match
}
```

### Malformed line handling

- Blank lines: skipped from the "parsed for prompt" list but line numbers still increment (to keep numbering aligned with the raw stored transcript for item 2's later verification).
- Lines that don't match the speaker/timestamp pattern (e.g., a stray note, a continuation line without a new timestamp): kept as `malformed: true`, and folded into the *previous* successfully-parsed line's `text` as a continuation (common in real transcripts where one speaker's turn wraps multiple lines) — but only if a previous line exists in the same non-blank run; otherwise treated as `malformed` and still included in the prompt as "unattributed text" so nothing is silently dropped from what's sent to the model. This directly matters for the "no decisions/action items omitted" trust principle — dropping content silently would be its own kind of data loss the product philosophy (CLAUDE.md, DECISIONS.md) explicitly argues against.
- If **zero** lines match the speaker/timestamp pattern at all → this is the "transcript too short / unparseable" edge case → 400 error before ever calling Gemini (saves a wasted Gemini call and gives a precise error).

### Handling long transcripts (1h, 8 speakers) and mixed Nepali/English

- Parsing itself is speaker-count-agnostic — no hardcoded speaker list, just regex per line, so 8 speakers is not a special case for the parser.
- Length: 1 hour at typical speaking pace is roughly 8,000-12,000 words. This is within Gemini 2.5 Flash's context window (1M tokens) with large headroom, so no chunking/truncation logic is needed for item 1 — flagging this as a decision (no chunking) rather than silently assuming it works.
- Mixed Nepali/English: the parser only touches timestamp/speaker structure (which is always in ASCII/Latin form — timestamps and typically speaker names), not the utterance content, so Unicode text (Devanagari or romanized Nepali) in the `text` capture group passes through untouched — no encoding-specific handling needed in the parser. The *prompt* sent to Gemini should explicitly instruct it not to drop non-English content (directly addressing DECISIONS.md's finding that Fathom silently ignored Nepali) — this is a `promptBuilder.ts` concern, not a parser concern.

### How line numbers reach evidenceQuote for later verification

The prompt given to Gemini includes each parsed line prefixed with its `lineNumber` (e.g., `[L14] [00:03:12] Alice: ...`), and the prompt instructs the model that `evidenceQuote` must be copied verbatim from the transcript content (not paraphrased) — but item 1's `EvidenceRef` type intentionally does **not** include a `lineNumber` field in the stored result, since exact verification-by-line-lookup is item 2's job and adding a possibly-wrong model-guessed line number now risks item 2 trusting a field it shouldn't. Item 2 will re-derive the line number itself by searching `transcript` for `evidenceQuote` server-side (normalized whitespace/case, per CLAUDE.md's item 2 description) rather than trusting anything the model claims about line numbers. This is a design decision worth confirming: item 1 stores enough (`evidenceQuote` as verbatim text + the full raw `transcript`) for item 2 to do its own lookup, rather than item 1 attempting a lookup it isn't scoped to do.
